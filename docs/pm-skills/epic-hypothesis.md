# Epic Hypothesis

**Type:** Component
**Source:** [deanpeters/Product-Manager-Skills](https://github.com/deanpeters/Product-Manager-Skills/blob/main/skills/epic-hypothesis/SKILL.md)

---

## Purpose

Frame major initiatives as testable hypotheses rather than feature commitments. Makes assumptions explicit, defines lightweight experiments, and establishes measurable success criteria before full build-out.

---

## Core Structure

```
HYPOTHESIS
If we [specific action]
For [clearly defined persona]
Then we will [measurable outcome]

TINY ACTS OF DISCOVERY
Lightweight experiment: [prototype / concierge test / landing page]
Timeframe: [2–4 weeks]

VALIDATION MEASURES
Success: [specific, falsifiable criteria]
Decision: Validated → convert to stories | Invalidated → kill or pivot
```

---

## Quality Checks

**Hypothesis:**
- "If we" must be specific — not "improve the product"
- Persona should be detailed — not "users" but "remote PMs managing 3+ teams"
- Outcome must be measurable — "50% faster" not "users like it"

**Experiments:**
- Fast (days/weeks, not months)
- Cheap (prototypes, not full engineering)
- Falsifiable (designed to prove you wrong, not confirm you)

---

## Common Mistakes

- **Confusing features with outcomes** — "Build a dashboard" describes output, not user benefit
- **Skipping experiments** — building full features before testing is feature development, not hypothesis validation
- **Unmeasurable success criteria** — "users are happy" can't guide decisions
- **Excessive timeframes** — 6-month validation cycles are too slow
- **Treating hypotheses as commitments** — running experiments as theatre when the feature is already promised
