# Proof of Life (PoL) Probe

**Type:** Component
**Source:** [deanpeters/Product-Manager-Skills](https://github.com/deanpeters/Product-Manager-Skills/blob/main/skills/pol-probe/SKILL.md)

---

## Purpose

The framework behind PoL probes — lightweight, disposable validation experiments designed to test a narrow hypothesis quickly before investing in full product development.

> "Reconnaissance missions, not MVPs — they're meant to be deleted, not scaled."

See `pol-probe-advisor.md` for the interactive version that helps you choose the right probe type.

---

## Five Essential Characteristics

Every PoL probe must be:

1. **Lightweight** — built in hours or days, not weeks
2. **Disposable** — explicitly planned for deletion to avoid sunk-cost thinking
3. **Narrow scope** — tests one specific hypothesis
4. **Brutally honest** — surfaces uncomfortable truths, not vanity metrics
5. **Tiny & focused** — smaller surface area for faster learning

---

## Five Prototype Types

| Type | Question It Answers | Timeline |
|---|---|---|
| Feasibility Check | "Can we build this?" | 1–2 days |
| Task-Focused Test | "Can users complete this job smoothly?" | 2–5 days |
| Narrative Prototype | "Does this workflow earn stakeholder support?" | 1–3 days |
| Synthetic Data Simulation | "Can we model this without production risk?" | 2–4 days |
| Vibe-Coded PoL Probe | "Will this survive real user contact?" | 2–3 days |

---

## PoL Probe vs. MVP

- **Probe:** Answers *if* you should build an MVP. Disposable. Days.
- **MVP:** Justifies shipping something. Survives beyond the experiment. Weeks.

---

## When NOT to Use

- Trying to impress executives with polish
- Seeking confirmation bias (you've already decided)
- Unable to articulate clear success criteria upfront
